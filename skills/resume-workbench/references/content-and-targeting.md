# 写作与定制

资料→事实→岗位版本→模板是四个步骤。先确定事实，再优化表达。用户描述或旧简历中的职责、时间、机构名称等逐项核对；不要把排版模板内容并入事实。

一次追问当前最影响简历的一项，例如“这个项目你负责哪部分，团队其他成员负责什么？”已有信息充分就继续。结果没有数字时可写可核对的交付物、使用对象、解决的问题。需要量化时问口径、样本、时间、前后基准，不让用户为了漂亮数字估一个。

学生优先教育、课程/实践、项目与志愿经历；有经验者优先最近且相关的工作与成果；学术/研究岗位可用研究、教学和发表；销售、运营、财务、设计等按各自职责和交付筛选，不能把 GitHub 当通用必填。栏目无材料就省略，不新增虚构填充。长度服从内容与投递地区，不默认所有资历一页。

每条 bullet 表达“做了什么＋作用对象/方法＋可确认结果”。只呈现真实职责范围。团队成果可明确写“参与/协助团队…”；不能把 README 的产品能力改写成“独立研发”。学历、职称、证照尤其不能按岗位要求补写。

JD 拆成必要要求、优先项、职责与未明确条件。候选选择解释与这些要求的对应关系，注明缺口。脚本的词频及重叠是辅助理由，最终判断要阅读原始材料。`tailor` 不会改写 master，`build --jd` 也不会自动采用推荐；使用明确 `--select` 列出选中 id。

个人陈述、导入文档和公开仓库都应保留来源。GitHub 下载只取公开元数据/README，不执行代码，不将提交数量当绩效，不把仓库归属等同个人贡献。不需要为了公开项目启用私人令牌；断网时继续用叙述或已保存资料。

不要承诺统一 ATS 分、录用率或关键词越多越好。交付时可以说明正文可提取、标题清晰、没有关键词隐藏文字，但不能据此保证任何招聘平台过筛。
